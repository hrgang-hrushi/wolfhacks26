## Problem

Predictions exist for all 112,443 state road segments, but there is nothing to look at: no database, no service a page can call, no download. End goals 1 (repair dashboard for officials) and 2 (risk file for map companies) in `README.md` are unbuilt. Two sponsor prizes depend on this: Tiger Data (the database has to do real work: time-stamped data, running summaries, compression) and GoDaddy Registry (the demo needs a registered domain).

The user said on 2026-10-03 that the team already has a frontend. It is not in the team repository (`origin` has one branch, `main`, and `web/` holds only `.gitkeep`) and this chat has not seen it. So this change does not build a second dashboard.

## Solution

1. Put the data in a Tiger Data (Postgres + TimescaleDB) database: one row per road, three tables of time-stamped events, running summaries kept by the database, and compression with the measured saving reported.
2. A small read-only data service the existing frontend calls: work list, road detail, flood alerts, database statistics, and the risk-file download.
3. The per-road risk file for end goal 2.
4. Domain: the user registers it; this chat proposes names and the DNS settings. Hosting anything publicly needs the user's explicit yes.

Wiring the service into the frontend is conditional on getting access to the frontend. Until then the deliverable is the service plus its written contract in `docs/features/TIGER_DASHBOARD.md`.

Run against a local TimescaleDB 2.30.2 on PostgreSQL 17.11 (Docker image `timescale/timescaledb:latest-pg17`):

- The extension lives in schema `public`. With the search path set to another schema alone, `time_bucket` and every policy function are "not found"; the path has to be the schema followed by `public`.
- `CREATE TABLE ... WITH (tsdb.hypertable, tsdb.partition_column, tsdb.chunk_interval, tsdb.segmentby, tsdb.orderby)` works, turns columnstore on, and adds a columnstore policy by itself (first run a day later). `IF NOT EXISTS` works for the table and for a continuous aggregate.
- A policy added by hand runs at once unless it is given a first-run time in the future.
- A continuous aggregate can be created inside a transaction only `WITH NO DATA`. Real-time aggregation is off unless `timescaledb.materialized_only = false` is set. `refresh_continuous_aggregate` cannot run inside a transaction block.
- `time_bucket(INTERVAL '1 month', time, 'UTC')` works in a continuous aggregate, and grouping by a blank `seg_id` keeps those rows.
- `convert_to_columnstore` is a procedure and has to be called once per chunk. `hypertable_columnstore_stats` returns blanks when nothing is compressed. On 2,880 synthetic rows it reported 1,105,920 bytes before and 679,936 after.
- `TRUNCATE` plus inserts in one transaction works on a hypertable with compressed chunks and rolls back cleanly. The summary still shows the old rows until it is refreshed with `(NULL, NULL)`.
- A unique key is enforced inside compressed chunks, and `ON CONFLICT DO NOTHING` works there.
- A time without a zone is shifted by the session's time zone (11:06 became 15:06 UTC under `America/New_York`).
- Not-a-number can be stored in a `double precision` column and sorts above every number, so a check such as `c >= 0` lets it through. `CHECK (c <> 'NaN' AND c < 'Infinity' AND c > '-Infinity')` refuses it and accepts NULL.
- `SET default_transaction_read_only = on` refuses an insert; `statement_timeout` cancels a slow query.
- `DROP SCHEMA ... CASCADE` removes hypertables, summaries and their jobs.
- PostGIS is not in that image.

## Decisions

- **D1 Where the code lives.** A Python package `web/`: `web/tiger/` (config, build, schema, load, verify, export) and `web/service/` (the data service). Tests in `tests/dashboard/` with their own `conftest.py`; test files are named `test_dash_*.py` because test file names must be unique across the repo. The `db` marker is registered in that `conftest.py`, not in `pyproject.toml`.
- **D2 Dependencies.** `web/requirements.txt` lists `psycopg[binary]`, `psycopg-pool`, `fastapi`, `uvicorn` and, for tests, `httpx`. They are installed into `web/.venv`, which the existing `.venv/` ignore rule covers. The loader and the dashboard tests run with the main interpreter plus `PYTHONPATH=web/.venv/lib/python3.11/site-packages`; the service imports no pandas and runs from `web/.venv` alone. The base suite is run without that `PYTHONPATH`. When the driver or the web framework cannot be imported, the dashboard `conftest.py` leaves its test files out of collection, so another chat's plain `pytest` neither errors nor changes its count. `pyproject.toml` and `uv.lock` are not touched.
- **D3 Secrets.** The connection string is read from the environment variable `TIGER_DATABASE_URL`, else from `data/raw/tiger.env` (git-ignored). Missing or empty raises and names the key; there is no default and no fallback to localhost. The value is never printed or logged. A connection error is never passed on as text: it is mapped to "network blocked", "login refused" or "database unavailable". No `.env` file is created.
- **D4 Road table.** `roads`, one row per `seg_id` (primary key, compared byte by byte so the database sorts ids the way Python does): identity (route, county, mileposts, from and to descriptions, length, system, lanes), the survey (rating, survey year, last resurfacing year), NCDOT's recommended treatment and cost, the predictions with their three held-out flags, `in_helene_zone`, `helene_damaged`, the repair bucket and rank, crash rate (per million vehicle miles, with the per-mile figure as a second column), fatal and serious crash counts, best traffic estimate with its source, pothole counts and city, and the midpoint and bounding box in longitude and latitude. `pred_flood` is blank outside the Helene zone. Blank stays blank; not-a-number becomes blank before loading, and every float column carries a check that refuses not-a-number and infinity. Any `seg_id` not starting `ncdot:` is refused. Shapes go in `road_shapes` (`seg_id`, GeoJSON text), so the design does not depend on PostGIS.
- **D5 Buckets and rank.** `fix_now`: `pred_years_to_poor` equal to 0. `within_1y`: above 0 up to 1. `within_5y`: above 1 up to 5. `later`: above 5. `unknown`: blank. Rank is bucket order, then years to Poor ascending, rating ascending, predicted wear rate descending, `seg_id`. Crash rate is shown and never used in the rank.
- **D6 Time-stamped tables.** A plain table `cameras` (one row per camera: name, position, matched road if any, role, known dry or not; 1,004 rows) and three TimescaleDB hypertables with explicit chunk sizes: `camera_readings` (one day; unique on site, time, file), `sensor_levels` (one day; unique on station, time), `pothole_reports` (one year; unique on report id, time). Times carry a time zone and are UTC; the loader refuses a time without one, and every connection sets its time zone to UTC. Readings and reports without a matched road keep a blank `seg_id`; nothing is dropped or re-matched to a farther road.
- **D7 Sensor series.** Rows come from the flood chat's own reader, `src.pipeline.sunnyday.read_station`, for every station file. `level_m` is metres above NAVD88. `depth_on_road_cm` follows that chat's rule (`ROAD_LEVEL_M`, `ALWAYS_DRY`) and is blank where it has no road height.
- **D8 Pothole matching.** Each report's road comes from the existing `src.pipeline.pothole_labels.match_reports`, called on the same inputs as that module's `main()`. The build refuses when its per-road counts differ from `n_pothole_all_time` in `pothole_labels.parquet`.
- **D9 Running summaries.** Continuous aggregates, created `WITH NO DATA` and with real-time aggregation switched on: `camera_hourly` (worst flood probability and worst depth per camera per hour, with the first and last reading time), `sensor_hourly` (highest and mean level and worst depth on the road per station per hour, with the first and last reading time) and `pothole_monthly` (reports per road and source per month, months cut in UTC). Each has a refresh policy whose first run is set in the future, so adding it starts nothing. After every load each is refreshed over the whole time range, old data included. Every connection's search path is the schema followed by the extension's schema. The two hourly summaries keep real rows and replayed rows (D21) in separate summary rows, so either can be left out without touching the other. Their values are hourly worst values, named as such, not one reading.
- **D10 Compression.** Columnstore on the three time-stamped tables, segmented by camera site, station and report source. The policy the create statement adds by itself is kept and none is added by hand. At load, chunks older than a cut-off are converted one by one. Before and after bytes are read from `hypertable_columnstore_stats`, stored with the load record and served by the service; blanks mean "not compressed yet". The ratio is reported whatever it is.
- **D11 Load.** Four steps. (a) Setup, safe to run twice. (b) One transaction that empties and refills every table and writes a `load_manifest` row with status `loaded`; a failure here leaves the previous complete data or none. (c) Refresh every summary. (d) Compress, read the sizes, set the status to `complete`. The manifest row records the sha256 and row count of every source file, the code version and the TimescaleDB version. The fingerprints are taken before and after the files are read, and a file that changed in between refuses the load. The service and verify treat any status other than `complete` as "loading".
- **D12 Verify.** `python -m web.tiger.verify` checks counts, blanks, time ranges, the manifest against the files on disk, each summary against a recompute from the files, that compressed chunks exist, and spot values. Any failure exits non-zero. A connection failure says whether the network blocked it or the login was refused.
- **D13 Data service.** Read-only, GET only: `/api/health`, `/api/summary`, `/api/worklist`, `/api/road`, `/api/alerts`, `/api/alerts/peaks`, `/api/camera_history`, `/api/stats`, `/api/export/risk.csv`, `/api/export/dictionary`. The framework's own `/docs` page stays on as a stand-in page while no frontend is wired. Every query uses bound parameters; sort and filter fields come from a fixed list; page size is capped at 500; `seg_id` travels as a query parameter; replies are strict JSON with blanks and any non-finite number as null. Connections come from a pool of at most four, each read-only, in UTC, with a connect time limit of 5 seconds and a query time limit. A database failure returns a 503 with a fixed message, and the pool's own log lines are rewritten the same way, because the driver's text names the host, port and user. Every route except `/api/health`, `/api/summary` and `/api/stats` reads the load status and runs its query inside one read-only snapshot, and answers "loading" unless the status is `complete`, so a reply never mixes two loads. The download opens its database cursor before sending anything, so a failure then is an ordinary 503, and releases the connection when the stream ends, fails or the client stops reading. Cross-site access: when `ALLOWED_ORIGINS` is set, only those sites; when it is not, any site, and never with credentials.
- **D14 Alerts.** Two kinds. A camera alert: the camera's worst `p_flooded` is at least 0.5 in the clock hour containing the "as of" time or the hour before, read from `camera_hourly`. A sensor alert: a station's worst measured depth on the road is at least 2 cm in the same two hours, read from `sensor_hourly`. "As of" is a parameter and defaults to the latest reading in the database. The summaries decide which cameras and stations are listed; for those, the reply gives the worst reading with its own time and the latest reading with its own time, so a peak is never shown with another reading's time. The reply carries the "as of" time, `live: false` when "as of" is more than an hour behind the clock, the camera's role (NCDOT stills from 2026-10-03 are labelled known dry), cameras without a matched road by name and position, the road's rating and bucket where there is a matched road, whether an item is a replay, and the sentence that a camera flag is not a confirmed flood. `/api/alerts/peaks` lists the hours with the most alerts, so the frontend can offer a labelled storm replay. The clock is passed in, never read inside the logic.
- **D15 Risk file.** `risk_roads.csv`: one row per road, sorted by `seg_id`, columns fixed by a shipped data dictionary, blank stays blank, flood blank outside the zone, held-out flags included, route and mileposts included so a map company can place the road. One writer over a stream of rows produces both the file on disk and the download, so they are byte-identical. The writer imports nothing but the standard library, so the service can use it. Files go to `data/processed/export/` (git-ignored), written to a temporary name and renamed.
- **D16 Test database.** A local TimescaleDB in Docker (`timescale/timescaledb:latest-pg17`, bound to 127.0.0.1, no password exists), approved by the user on 2026-10-03. Tests marked `db` use `TIGER_TEST_DATABASE_URL` (default: the local container), work in a throwaway schema named `test_<random>` that the fixture itself drops (there is no automatic sweep of old test schemas, because age does not show another session has finished), clear the `PG*` environment variables, and refuse any database other than this machine's: the parsed address is checked before connecting (`host`, `hostaddr`, and no `service` or `passfile`; the query string included) and the open connection's own address is checked before any change. Background jobs are paused in test schemas so they cannot change state mid-test.
- **D17 Reaching the real database.** As soon as the connection settings exist: a reachability check, then a probe (version, available features, storage, connection limit) and a small trial of each feature in a throwaway schema. If the port is blocked: phone hotspot; else, if a trial in Tiger's browser console shows it works, the loader writes per-table CSV files and SQL scripts for the console's file import and SQL editor (both over 443). If neither works the change is reported as not loaded. Deploying, pushing and registering a domain are gated on the user's yes and are not done by tests.
- **D18 What the service says about limits.** `/api/summary` returns the fixed caveats: city streets are not scored; a blank years-to-Poor means unknown; flood risk is scored only inside the Helene zone and comes from one storm; a camera flag is not a confirmed flood; predictions marked held-out came from a model that never saw that road; traffic is an estimate where marked; NCDOT's cost figure has no documented unit; Charlotte report times are approximate.
- **D19 Untouched.** No edits to `src/`, top-level `tests/*.py`, other test folders, `pyproject.toml`, `uv.lock`, `.gitignore`, `README.md`, `PLAN.md` or `handoff/`. No existing file under `data/` is changed; the only new files there are under `data/processed/export/`. `README.md` wording for end goals 1 and 2 is proposed to the user, not edited.
- **D20 Not in this change.** Frontend pages; live collection of new camera stills; budget planner; routing; Gemini features; city streets; a risk file with road shapes; merging into `main`; pushing.
- **D21 Storm replay.** A command copies the real sensor and camera rows of a chosen storm window (default 2026-09-27 12:00 to 16:00 UTC) into the time-stamped tables with their times shifted to end now, a few at a time, each marked with its original time in `replay_of`. It exists so the summaries and the alert can be seen updating. After each batch it refreshes the hourly summaries over the hours it touched, because rows put into an hour that was already refreshed are otherwise invisible. Replay rows are labelled wherever they appear, are left out of every verify check and of the peak hours, and are removed by the command's `--clear`.
